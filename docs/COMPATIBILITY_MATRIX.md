## Local queue repeat contract

The repeat controls use these explicit public-client modes:

| Behavior | HTTP `loop` / PlayQueue `LoopMode` | AVTransport `NewPlayMode` |
| --- | --- | --- |
| Sequential default | `4` | `NORMAL` |
| Repeat selected item | `1` | `REPEAT_ONE` |
| Repeat queue, wrapping last to first | `0` | `REPEAT_ALL` |

Use `setPlayerCmd:loopmode:N`, standard `SetPlayMode`, or vendor
`SetQueueLoopMode` with `LoopMode`. The vendor setter accepts an optional
nonempty `QueueName` only when it matches the current queue; the getter needs no
arguments. `GetTransportSettings` returns `PlayMode` and
`RecQualityMode=NOT_IMPLEMENTED`. HTTP status, queue XML, SOAP and GENA derive
from the same queue policy; AVTransport LastChange includes `CurrentPlayMode`.
Repeat controls and the shuffle extension below share that authority; RANDOM and informal aliases fail without mutation.

The mapping is evidenced by [pywiim's public loop-mode adapter](https://github.com/mjcumming/pywiim/blob/main/pywiim/api/loop_mode.py)
and independently by [wiimplay's PlayQueue values](https://github.com/shumatech/wiimplay/blob/ca9507803266b454b9072faa8556ba70f5931817/wiimdev/types.go#L47-L55)
and [SOAP setter](https://github.com/shumatech/wiimplay/blob/ca9507803266b454b9072faa8556ba70f5931817/wiimdev/wiim.go#L155-L157).
The [official WiiM HTTP API v1.2](https://www.wiimhome.com/pdf/HTTP%20API%20for%20WiiM%20Products.pdf)
read table agrees, but its write table assigns `0` to sequential and `-1` to
repeat-all. ORR deliberately uses the public-client dialect; there is no automatic
dialect detection or original-app certification.

**Compatibility correction:** earlier ORR called `0` normal, which public clients
read as repeat-all. Sequential behavior remains the default but now reports `4`.
Omitted queue mode defaults to `4`; explicitly supplied `0`, including externally
saved old queue XML, now means Repeat All. Change such old documents to `4` for
sequential playback. ORR has no persisted queue-state migration in this package.

Repeat applies to observed finite-media end. In these repeat modes, multi-item Next/Previous remain
numerical and nonwrapping (singleton Previous retains seek-to-zero), following the [AVTransport:1 contract](https://upnp.org/specs/av/UPnP-av-AVTransport-v1-Service.pdf);
Repeat One does not trap manual Next. Mode changes alone do not restart playback,
bump owner generation, resume paused media or clear errors. Live-station recovery
keeps precedence and its finite retry budget. Failed repeated loads remain errors.
Existing snapshots do not carry mpv end-file reasons: an unclassified post-ready
source termination can also repeat. This is not reason-aware failure recovery.

Opt-in native successor staging remains NORMAL-only. An actual mode change with
an armed/owned native playlist, pending cleanup or uncertain output fails unchanged.
Use confirmed Stop → set mode → Play; an unconfirmed Stop does not release the
fence. Repeat uses normal confirmed loading and makes no gapless-repeat promise.

## Editable local favorites

The renderer-owned JSON library is separate from OEM/provider preset-write APIs.
Existing public `getPresetInfo`, `MCUKeyShortClick:N[:1]` and `preset_key` share one
effective view: unchanged configuration-owned prefix followed by managed entries.
Stable managed IDs identify edits and owned recall; numeric slots are dense and can change after
removal. Recall still selects one direct target, including a playlist/container
URL; it does not resume an old multi-track position.

| ORR endpoint | Request | Success |
| --- | --- | --- |
| GET `/orr/v1/favorites` | None | Versioned list with id, slot, editable, name, url and display fields |
| POST `/orr/v1/favorites` | name, url; optional title/artist/album/artwork | 201 and created favorite |
| POST `/orr/v1/favorites/current` | name | 201 and canonical selected direct target |
| POST `/orr/v1/favorites/ID/play` | No body | 200 and `{"request_acknowledged":true,"favorite_id":"ID"}` |
| PATCH `/orr/v1/favorites/ID` | name | 200 and renamed favorite |
| PUT `/orr/v1/favorites/ID/target` | Exactly url and metadata (`keep` or `clear`) | 200 and updated favorite |
| DELETE `/orr/v1/favorites/ID` | No body | 200 and deleted ID |

JSON-bearing writes require UTF-8 JSON, bounded Content-Length and no compression/chunked
transfer. Limits: 100 managed entries, 1MiB stored JSON, 32KiB request, 256 UTF-8
bytes for name, 1024 each for title/artist/album, 8192 each for URL/artwork.
Duplicate fields/IDs, unknown schema fields/versions, invalid types and malformed
XML text fail. HTTP(S) URL bytes and query encoding are preserved; userinfo and
renderer audio-proxy paths, including encoded/dot-segment equivalents, are rejected.
No library edit fetches media or changes the active queue, generation, position,
volume or play mode. Playback still goes through the existing selected-URL path.

Target repair preserves managed ID, library name and position. Its exact JSON
body is `{"url":"https://media.example.test/repaired.wav","metadata":"keep"}`
or the same shape with `"metadata":"clear"`. `keep` preserves title/artist/album/
artwork; `clear` empties exactly those four fields. The metadata policy is required
in both API and CLI (`favorites set-url ID URL --metadata keep|clear`). Unchanged
records are acknowledged without a disk write. Configuration-owned targets remain
read-only (403); unknown managed IDs return 404. Missing/extra fields, invalid URLs
or metadata choices return 400; other methods on this target route return 405.
Existing name PATCH and save-current POST contracts are unchanged.

The success body remains the exact `{"favorite":{...}}` envelope with ID, slot,
editable, name, URL and all four display fields. It is returned only after the
store transaction succeeds (or no-op). The dedicated target-edit CLI requires
HTTP 200, identity-encoded UTF-8 application/json, a bounded response (128KiB),
exact fields, matching ID and URL bytes, editable=true and a positive integer
slot. Clear-policy ACKs must have four empty display fields. It uses one direct
PUT with environment proxy/netrc discovery disabled, without preliminary reads,
redirects, retries, rollback or legacy-client fallback. Its output contains only
request_acknowledged, favorite_id and metadata policy. On 503 it reads at most
4KiB to recognize only the owned durability-unconfirmed/committed=true warning;
remote error text is never printed. Other malformed/oversized ACKs and transport
failures leave the outcome unconfirmed. Its 10-second connection/read-inactivity
timeout is not a total execution deadline.

Owned recall accepts a managed ID or strict `configured:N` (one to six digits,
positive and no leading zero). Configured IDs identify configuration slots and
can change meaning if that configuration is reordered; managed IDs are stable.
It resolves a detached effective-preset snapshot
under the library lock, preserving source and artwork, before awaiting playback.
Later edits cannot retarget that request; deletion before admission returns 404.
Malformed IDs or any body/chunked transfer return 400, managed-library unavailability
returns 503, and backend/resolver failures return a fixed private-safe 502. Existing
playback ownership, cleanup and recovery rules apply. The acknowledgement is not
a continuing audio observation. The CLI requires that exact bounded acknowledgement
and HTTP 200; it makes one request without redirects or retries, with an explicit
unconfirmed-outcome warning on timeout.

A corrupt/unreadable store is preserved: managed API reads/writes return 503 while
configuration-owned recall and unrelated playback remain usable. Pre-replace
storage failure returns 503 with committed=false and keeps previous memory/file.
After replacement, unconfirmed directory durability returns 503 with committed=true
and retains the new in-memory view; the CLI emits a fixed read-before-retry warning.
The separate atomic-helper correction avoids unnecessary post-replace temp cleanup
masking a committed result. This is one-process local persistence, not a multi-writer
transaction system or power-loss certification.

Save-current rejects unresolved selections and malformed or mismatched resolver
provenance. For a proven live station it saves the fixed anonymous reference
`https://opml.radiotime.com/Tune.ashx?id=s12345&formats=mp3,aac&render=json`, using only
the strict public station ID from trusted successful-resolution provenance. The
original selection URL must still match that provenance, type must be station,
and duration must be a valid numeric zero. Public labels/XML/JSON cannot establish
that private tuple. Saving never resolves; explicit recall resolves afresh and
uses existing station recovery. Direct nonresolver URLs stay byte-for-byte.
It never copies temporary/backend/proxy URLs, separate provenance/account fields
or raw provider metadata. Existing display authority is retained: a captured
live-song title may remain fixed on recall. The [official station-ID guide](https://broadcaster-help.tunein.com/en/support/solutions/articles/151000172143-what-is-my-station-id-)
identifies public s-prefixed station IDs. This reuses the resolver endpoint already
observed anonymously on October 11; no new provider contract, account or partner
API is introduced. Fresh WAN availability remains unverified; controlled resolver
and real local backend evidence do not establish provider uptime.
The interface adds no authentication or CORS and is not safe for Internet exposure.
Queries may contain secrets the validator cannot recognize; users must not save
credential-bearing or temporary signed URLs.

The [public pywiim preset API](https://github.com/mjcumming/pywiim/blob/0daa35f8e374eae818bd88795f3ef50b684adf86/pywiim/api/preset.py)
and [official HTTP API section 2.8](https://www.wiimhome.com/pdf/HTTP%20API%20for%20WiiM%20Products.pdf)
provide list/recall, not a complete generic direct-URL edit contract. Public
SetKeyMapping wrappers do not establish a complete saved target, so ORR does not
invent that OEM write behavior. Original-app/hardware acceptance remains pending.

## Shuffle traversal and navigation

Public HTTP/PlayQueue mode `3` means shuffle once; `2` means shuffle with Repeat All.
Both report standard AVTransport `SHUFFLE`, which cannot express the combined
repeat flag. Explicit `SetPlayMode(SHUFFLE)` chooses mode 3. This is an intentionally
lossy projection; numeric LoopMode retains the distinction. `RANDOM` remains
unsupported, rather than being guessed as an alias. The AVTransport specification
lists those values without defining an exact random/repeat distinction; pywiim's
normal shuffle toggle preserves Repeat All and therefore needs numeric mode 2.

Canonical queue items stay in their original order and public indices remain
one-based. Entering shuffle anchors a cycle at the current selection and permutes
all remaining indices. Mode 3 finishes that cycle and stops; mode 2 generates a new
complete permutation, avoiding immediate repetition across the boundary when
there is more than one item. Duplicate URLs still occupy distinct positions.

- HTTP `next`/`prev` follows shuffle history. Previous can return through the current
  and one preceding cycle; Next retraces that path without drawing again.
- Multi-item SOAP Next/Previous stays canonical numerical and nonwrapping, following
  the standard contract. Singleton SOAP Previous retains its existing seek-to-zero
  behavior. Explicit indexed selection and SOAP navigation start a fresh cycle.
- Same-mode requests are true no-ops, including RNG state. Switching 2↔3 preserves
  order/cursor; leaving shuffle discards history. New/replaced queues get fresh
  traversal and their supplied/default mode. Preset recall creates a fresh queue;
  editing the favorite library alone never changes the active queue or mode.
- Pause/Resume/Seek and ordinary Stop preserve traversal. Play after ordinary Stop
  retries the selected item and continues the remainder. Play after natural
  shuffle-once exhaustion starts a fresh cycle anchored at the last selected item.
- History is private, nonserialized and bounded to two cycles, at most 2000 indices.
  Metadata updates and station URL refreshes do not reset it.

Successor checks do not consume randomness or history. After required Stop/source
checks succeed, current policy is re-read and canonical index/history commit
without another await before the existing load path. Failed or superseded Stop
consumes nothing; a failed load retains that selection with ERROR and never skips
randomly to another item. Owner/source/generation fences, finite station recovery
and normal-only native staging restrictions remain. Shuffle makes no gapless claim.

## Renderer-owned queue CLI and authored files

`queue show`, `queue load`, `queue play-index` and `queue mode` are local convenience clients
of the existing PlayQueue SOAP service, not new renderer actions. `load` sends
one ReplaceQueue with QueueContext only; it replaces the complete queue and stops
playback. Its selected one-based index is silent unless `--play` explicitly follows
with PlayQueueWithIndex. That second request is sent only after an exact successful
replacement response. `play-index` always requests playback, without rewriting
the queue. Different-name requests fail; a name is not a revision/CAS token for
concurrent same-name replacement.

`queue mode MODE` sends one SetQueueLoopMode with **LoopMode only**, as declared
by the service's SCPD, and requires the corresponding empty SOAP success response.
It addresses the current queue without a name/revision guard, replacement, browse
or Play request. A rejection/uncertain response never triggers another mutation.

The local `next`, `previous`, `mute on|off` and `seek SECONDS` CLI controls map to
existing `setPlayerCmd:next`, `setPlayerCmd:prev`, `setPlayerCmd:mute:1|0` and
`setPlayerCmd:seek:N`. Navigation deliberately uses HTTP shuffle/history semantics,
not SOAP numeric Next/Previous. Seek input is a nonnegative ASCII integer absolute
position; state, media and duration admission remain renderer responsibilities.
Existing stopped/paused intent is preserved. These client commands accept only
HTTP 200 with the complete literal two-byte `OK` acknowledgement, bound both
read chunks and accumulated response bytes, and never print remote error bodies. They share
queue host/port validation, disable redirects/environment proxy/netrc/retries,
close their response/session, and use the same 10-second connect/read inactivity
timeout. Acknowledgement is not observed playback; uncertain requests tell the
user to inspect status before deciding whether to retry.

`show` projects canonical order, count, index and mode. URLs and opaque/display
metadata are omitted by default. The explicit `--include-urls` output is labeled
renderer-reported and potentially resolved/credential-bearing. BrowseQueue uses
resolved URLs where present, so these bytes are not claimed as canonical export.

`playlist create` authors a strict version-1 JSON file from supplied URLs only:
`version`, `name`, `index`, `mode`, `urls`. It does not contact the renderer or
capture runtime metadata, position, account state or shuffle history. `restore`
validates all content and the complete escaped SOAP frame before making the same
single replacement; no autoplay unless requested. Unknown/duplicate fields,
nonfinite values, invalid exact types/indices/modes/XML/UTF-8 and oversized inputs
fail before mutation. Limits are 1000 URLs and independent 1 MiB file/request
bounds. HTTP(S) URL bytes are preserved; whitespace, userinfo and reserved renderer
proxy targets are rejected. Raw CR queue names are rejected because they cannot
round-trip through the existing server's SOAP acknowledgement.

`playlist save-current FILE --host HOST --port PORT` performs one bodyless GET to
`/orr/v1/queue/playlist` on the existing listener. It adds no bind, authentication
or CORS change; like existing controls this is for the intended trusted LAN.
Only HTTP 200 with identity-encoded application/json is accepted. Strict v1 decode,
ordinary URL validation and the full escaped restore-request bound complete before
any output temporary. Redirects, environment proxy/netrc, retries and old-server
fallback are disabled. Files use existing private atomic no-clobber publication;
this command offers no overwrite or play flag. Playlist GET responses carry Cache-Control:
no-store, and neither payloads nor remote errors are logged by these adapters.

The server captures one queue reference and synchronously detaches validated bytes
before yielding, without backend synchronization, resolution, media fetches,
favorite-store access or filesystem work. All five modes, selected one-based index,
name, canonical order and duplicates survive. Every item is checked: malformed or
stale radio provenance cannot fall back to a potentially temporary item.url.
Locally proven radio stations use only their fixed anonymous public reference;
ordinary URL bytes remain unchanged. Unproven direct station classifications are
rejected because a plain-URL restore would lose their live/recovery semantics.
An unresolved explicit public station reference remains an ordinary URL and is
not resolved during saving. HTTP 409 has one data-free error for any unavailable,
invalid, empty/provider-only, oversized or unrepresentable queue. Unexpected body
or query input returns 400; other methods, including HEAD, return 405.

This projection drops all display metadata, durations, provider/source fields,
IDs, opaque metadata, playback position/state, shuffle history and provenance.
It is a URL playlist, not a lossless backup or an account/provider export. Ordinary
originally supplied temporary/token-bearing URLs cannot be identified reliably;
files remain private and future playability is not guaranteed. The snapshot is
coherent at capture; later queue changes do not invalidate it or imply CAS.

`playlist import-m3u INPUT OUTPUT --name NAME` is an offline converter into that
same authored JSON format, with index 1 and normal mode. It accepts only the
[documented UTF-8 URL-list subset](../GETTING_STARTED.md#multi-track-queues-and-authored-playlists):
optional exact EXTM3U, simple paired EXTINF (discarded), explicit human comments
and exact HTTP(S) URL lines. Unknown directives, including HLS and player options,
fail closed. It neither fetches nor expands remote content, and makes no remote
playability or valid-boundary truncation claim. An `.m3u8` suffix does not decide
acceptance. The input, generated JSON and complete SOAP request have independent
1 MiB limits. Existing output, including aliases of input, cannot be overwritten.

`playlist append INPUT OUTPUT URL...`, `playlist remove INPUT OUTPUT --index N`
and `playlist move INPUT OUTPUT --from-index N --to-index M` edit valid v1 JSON
files offline. They preserve name/mode, exact URL bytes and duplicates. The
selected occurrence is tracked by original position, never URL equality. Append
preserves its index. Removing before selection decrements the index; removing
after selection preserves it. Removing the selected occurrence selects the next
surviving neighbor at the same final index, or the final previous item. Removing
the only item fails. Move's destination is its final one-based position after
removal; a same-position move still writes a new equivalent output. Positive
ASCII indices reject signs, whitespace, leading zeros and out-of-range values.

The complete source and result must pass schema, explicit-URL and escaped SOAP
validation, so removing an invalid final entry cannot repair an invalid file.
Independent 1 MiB input/output/request and 1000-item bounds remain unchanged.
Input bytes are untouched, and output must be new, including no input aliases.
There are no overwrite, host, port, name/mode or play flags. Editing constructs no
HTTP session, performs no resolver/media/backend work, and changes no playback.
Explicit restore remains separate and stopped by default. The format still omits
metadata, playback state/position, history and provenance; private URL-bearing
files carry no future-playability guarantee.

Files require an existing parent directory, private 0600 temporary writes and
atomic publication. Creation never clobbers an existing destination; overwrite
requires its explicit flag. Known final symlinks/nonregular files are rejected;
this is not protection against an adversarial concurrent filesystem path swap.
A post-publication durability failure reports that the new file is already saved.
These user-authored files may contain URL query secrets and are not share-safe
exports. They are distinct from the server's settings and favorites persistence.

SOAP responses require the expected namespace/action and unique scalar fields;
generic HTTP200 or unrelated XML is not success. Requests do not follow redirects,
use environment proxies/netrc or retry mutations. Response reads are byte-bounded;
the 10-second requests timeout is connect/read inactivity, not a total wall-clock
transaction deadline. An uncertain replacement prevents Play, while a confirmed
replacement followed by uncertain Play reports partial success without rollback.
Acknowledgement is not an assertion of observed audio. Inspect queue/status before
retrying. No new listener, authentication policy or playback-core behavior follows
from these client commands.
